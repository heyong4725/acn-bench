# ADR-3 — What `trace-check` counts as implemented, and how citations are parsed

**Status:** accepted (T01). **IDs affected:** CON-12, CON-23.

## Context
CON-12 says `cargo xtask trace-check` MUST fail when "a MUST in an implemented spec section has no citing test", but nothing in the specs marks a section as implemented, and specs are read-only for agents (CON-14). The check also needs unambiguous rules for what a `/// Cites:` comment is and where it may sit.

## Decision
1. **Scope file.** `trace-scope.toml` at the workspace root lists, per spec, the `sections` (by `## N.` heading number) and/or individual `ids` that are implemented. The PR that implements a MUST adds it to the scope. IDs outside the scope are still valid citation targets, so tests may cite ahead of full implementation; only in-scope MUSTs are required to be cited. Unknown IDs and empty sections in the scope file are errors.
2. **Requirement IDs** are paragraphs in `specs/<NNN>-*.md` that begin with a bold ID (`**CON-5**`). The level is the strongest RFC 2119 keyword in the paragraph (`MUST NOT` counts as MUST). Fenced code blocks are ignored. Duplicate definitions are an error.
3. **Citations** are `/// Cites: ID[, ID…]` doc-comment lines in `.rs` files under `crates/` and `tests/` (a line ending in `,` continues on the next doc line). They must be attached, through further doc lines and attributes placed before or after the doc block, to a `fn` carrying a test attribute, meaning an attribute whose path ends in `test` (`#[test]`, `#[tokio::test(...)]`, `#[cfg_attr(..., test)]`); `#[cfg(test)]`, `#[doc]` and third-party runners such as `#[rstest]` do not qualify. A citation on a non-test function, on anything that is not a function, a malformed ID, a misspelled marker, or an empty list fails the check. `lab/` is not scanned (CON-23). Directories named `target` or `fixtures` are skipped so self-hosting fixtures can contain deliberately broken citations.

## Consequences
Coverage is declared, not inferred: a reviewer can see in one file which MUSTs a PR claims. `docs/generated/requirements.md` renders the same model, so drift between spec, scope and tests is visible on every PR. Section-level scope lets a spec task claim a whole section at once; ID-level scope handles constitution clauses that are implemented piecemeal.

## Known limits of the spec grammar
The parser recognises an ID only when its bold form starts a line; bold IDs mid-line or inside tables are references, not definitions. Only `## N.` headings set the section (`### N.M` does not). A `MUST` inside backticks or a code fence counts as prose in the first case and is ignored in the second; spec authors keep normative keywords out of code spans. A root with no `specs/<NNN>-*.md` files is an error, not an empty pass. Duplicate ID definitions, within or across files, are an error.

## Amendment 1 — every in-scope ID needs a citation, whatever its wording
CON-12 speaks of "a MUST in an implemented spec section", and the first version of the check required a citation only for paragraphs containing the keyword MUST. A third of the published IDs carry no RFC 2119 keyword because they are written as profiles ("Required: …"): the whole span profile TRC-10..17, the bundle layout TRC-22 and the derived views TRC-31..34 in SPEC 010, and CON-6 and CON-9 in the constitution. Under the keyword rule the trace-schema task could have passed the gate with no tests for its core. The scope file is the declaration of what is implemented, so `trace-check` now requires a citing test for **every** ID the scope lists, and reports each missing ID with its level. The keyword level is kept for the inventory only. Tightening the spec wording itself is a `spec-change` matter; it is drafted in the foundation `spec-change` PR of the same series.

## Amendment 2 — ID references outside Rust are validated
Markdown at the root, under `docs/` and under `specs/`, and the files under `hypotheses/`, are scanned for `PREFIX-n` tokens. If the prefix belongs to a written spec, the ID must be defined there, otherwise the check fails with a dangling reference. If the prefix is only listed in the `specs/README.md` index (a spec still to write), the token is reported as a forward reference and does not fail. Any other token (`UTF-8`, `ADR-3`, `H-1`) is not a requirement ID. A range such as `TRC-10..21` (or with an en dash) names both endpoints, and both are checked. A hypothesis file is parsed as TOML and its `[poc].spec`, however quoted, must be a path of the form `specs/<file>.md` that exists or is listed in the index; a file that is not valid TOML fails the check. `docs/generated/`, `docs/lab/` and `lab/` are not scanned (CON-23), and inside `specs/` fenced code blocks are skipped as example text, matching the spec parser. When a spec is written, its forward references become checked references automatically.
